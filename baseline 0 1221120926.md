## 1. What Causal Affect is

Causal Affect is an **autonomous business-generation engine**. It watches a wide universe of external signals (Wikipedia pageviews, Reddit activity, FRED economic indicators, Google Trends, GDELT news tone, arXiv paper counts, stock data), finds statistically causal relationships between them, turns those relationships into scored commercial opportunities, and then **builds, deploys and monetises small web apps** to exploit those opportunities — measuring the results and feeding them back so the next cycle is better.

The patent title captures it precisely: *"System and Method for Autonomous Cross-Domain Causal Discovery and Business Generation using Ensemble Prediction and Test-Driven Development."*

It is **not** a dashboard for humans to find ideas. The human's role is deliberately restricted to reading recommendations, selecting one to build, and auditing the evidence. Every recommendation must originate from the system's own Discovery stage — manual idea entry is explicitly out of scope (Track I of the scaling plan).

## 3. The core architecture: a six-stage self-correcting loop

Everything exists to serve one loop, which must run without human gates:

1. **Discovery** — Ingest signals daily (APScheduler jobs), run Granger causality / correlation across variable pairs, and generate `ExploitationRecommendation` records (BUY / SELL / BUILD / MONITOR) with an opportunity score, build-viability score, market size, competition level and predicted direction.
2. **Adapt** — For a BUILD recommendation, an AI spec generator writes a YAML specification with acceptance criteria and test scenarios, sized by complexity tier (LOW/MEDIUM/HIGH → 4/7/12 criteria).
3. **Exploit** — The MVP builder runs a five-phase TDD cycle: SPEC → RED (failing tests) → GREEN (implementation, up to 5 retries, ≥80% pass rate) → REFACTOR → VALIDATE/VERIFICATION (traceability artefacts). It then pushes to a new GitHub repo (`github_service.py`), provisions Railway (`railway_service.py`), and wires Stripe (`stripe_service.py`). The `mvp-NN-*` public repos on the account are the output of this stage.
4. **Monitor** — The deployed app should carry a beacon keyed by `build_id`: GA4 for engagement, Stripe metadata for revenue, joined in a `BuildTelemetry` table (`build_telemetry_service.py`, `ga4_service.py`).
5. **Learn** — Correlate verification status, prompt versions, spec attributes and telemetry to find what predicts engagement and revenue. Track A's ensemble model (Granger 40% / OLS 35% / ARIMA 25%) calibrates its weights from validated predictions once ≥10 exist.
6. **Optimise** — Feed findings back into recommendation weighting and prompt selection. Initially read-only findings on the Program Baseline panel; auto-rotation deferred to M5+.

The operating principle stated in the plan: *when build quality is poor, fix the loop's learning — never insert a human gate.*

## 4. Key subsystems and where they live

- **Data universe**: `data_fetcher.py`, `data_source_registry.py`, `seed_fred_variables.py`, `seed_gdelt_variables.py`; TimescaleDB hypertables with pool tuning.
- **Causal analysis**: `granger_causality_service.py`, `correlation_analyzer.py`, `walk_forward_validator.py`, `ensemble_model.py`.
- **Exploitation scoring**: `exploitation_backtester.py`, `product_concept_generator.py`; scoring weights per the CA-002 spec (significance 30%, effect size 25%, stability 20%, actionability 15%, market size 10%).
- **Build pipeline**: `spec_generator.py`, `ai_code_generator_orchestrator.py`, `mvp_builder_service.py`, `verification_engine.py`, `build_error_classifier.py`, `build_intelligence_service.py`.
- **Deployment & monetisation**: `github_service.py`, `railway_service.py`, `stripe_service.py`, `s3_service.py`.
- **Commercial intelligence**: `commercial_intelligence_service.py`, `ProductDeployment` / `ProductMetrics` models.
- **UI**: a single dashboard (`templates/dashboard.html`, `static/js/dashboard.js`, `routers/dashboard_real.py`) with tabs for Signal Radar, Exploitation Board, Prediction Accuracy, Revenue, and Program Baseline.

## 5. What "Baseline 0" means

The definition hard-coded in `control_tower/scripts/baseline0_audit/report.py`:

> A user reads recommendations, selects one, and Causal Affect builds it, tests it, ships it to GitHub, deploys it to Railway, wires GA4 and Stripe, optimises it for search, collects engagement and revenue, displays performance, lets the user iterate the winner, and learns from the outcome so that the next recommendation, build and iteration are measurably better.

The audit decomposes that into **fifteen links** (B1–B15), each of which must be backed by code *and tests* and, where possible, confirmed against the live site:

| # | Link | # | Link |
|---|---|---|---|
| B1 | Recommendations visible to the user | B9 | SEO on the deployed app |
| B2 | Select-to-build trigger | B10 | Engagement collected into storage |
| B3 | AI code generation | B11 | Revenue attributed back to the app |
| B4 | Test gate — pipeline refuses to ship failing code | B12 | Performance dashboard |
| B5 | Ship to GitHub | B13 | Scoring maths correct (revenue 40 / engagement 30 / conversion 20 / retention 10) |
| B6 | Railway deployment live | B14 | Iterate the winner with lineage (`parent_build_id`) |
| B7 | GA4 wired with a real measurement ID | B15 | Learning loop actually changes weights and improves on holdout |
| B8 | Stripe can take a payment | | |

Phase A checks preconditions (both repos present, "COMPLETE" claims in planning YAML actually backed by code, no placeholder IDs or secrets in production). Phase C walks B1→B15 and reports **the first broken link** — that link, not the longest gap list, is the real Baseline-0 blocker.

Importantly, Baseline 0 is **not** the milestone gates in the scaling plan (65% accuracy, 500GB data, etc.). It is a narrower question: *does one recommendation survive the whole loop end-to-end, with evidence?* It sits underneath M0–M2 as the thing that has to be true before the accuracy and scale targets mean anything.

- **Anti-drift** — the "Add Your Own Idea" manual path still exists in the dashboard and must be removed (M2-OA-15, priority HIGHEST).
- Ensemble direction accuracy is 49.3% vs the 65% M2 target — relevant to the *quality* of the loop but not a Baseline-0 blocker.

## 7. Guardrails any automation must respect

- Never write to production; Stripe only in test mode.
- Never insert human approval gates for specs, ACs, or code.
- Never use mock/placeholder data in production (`G-XXXXXXXXXX` etc. are audit failures).
- Every build must originate from a Discovery recommendation and be bound to telemetry by `build_id`.
- Evidence (specs, verification artefacts, telemetry) must be exposed read-only.
- Results should reach the owner via the tracking issue → GitHub Mobile notification, with a plain first line saying whether the run needs them.
